# Auto mode and inherited tool permissions

Auto mode runs at Pi's pre-execution `tool_call` event. The package loads it last so it checks this package's final routed inputs; a manifest regression test preserves that order. Later third-party mutation handlers remain trusted extension code. Canonical workspace reads and edits are model-free. Policy and routing share Pi's path normalization for home expansion, leading `@`, `file://` URLs and Unicode spaces. Read checks also select Pi's existing macOS filename fallback before canonicalization, so fallback symlinks cannot change the checked destination. Repository control files, common credential paths such as `.env`, `auth.json`, and private SSH keys, and paths escaping through symlinks need approval. Filename checks cannot identify every secret. Pi's `grep` includes hidden files. Directory/default searches therefore require explicit approval; model-free grep is limited to a specific regular nonsensitive file. Children without interactive approval block directory searches. Only literal `pwd` is automatically allowed shell execution; composed shell commands require approval even if classification says safe. We deliberately do not parse shell grammar into an incomplete allowlist.

Uncertain calls use a tools-disabled request to the selected provider, with up to twelve recent conversation messages bounded to 12,000 characters and a ten-second deadline. Audit and custom extension entries are excluded. The request allows 2,048 output tokens, asks for minimal reasoning through the SDK adapter, and leaves provider-specific thinking budgets at the SDK defaults. The SDK clamps unsupported reasoning levels to the model's supported level. Case, surrounding quotes, and a terminal period are accepted around a single verdict; extra text, missing output, and provider errors block execution. Live provider behavior is not verified by the offline tests. Classification failures block execution. An `ask` decision requires a functioning TUI or RPC confirmation UI. The approval dialog contains the complete action input, canonical cwd and target, and provenance, without classifier context or directives. Large action inputs remain complete. Exact approvals bind the entire action, canonical cwd and target, provenance, session scope, policy fingerprint, and directives. Changing conversation output does not invalidate an exact approval; that bounded context is only classifier input. New interactive or RPC user directives, mode changes, and routed workspace changes invalidate approvals. `/auto on|off|status|audit` controls and explains the policy. Session entries preserve final decisions; an in-memory bounded audit also tracks directives, actions, declarations and approvals.

After `session_start`, trusted local extension code may emit `auto-mode:declare` with `{version:1, source:'local', extension:absoluteLocalPath, tool, effect:'read'|'write', pathArgument}`. This is an in-process trust API, not permission inferred from remote MCP metadata. A declaration may instead use `effect:'managed'` without `pathArgument` for an extension's bounded internal storage or UI operation. The declaring trusted extension owns validation of those effects; auto mode still checks canonical cwd containment and inherited tool permissions. The bundled memory, todo and questionnaire extensions respond to `auto-mode:request-declarations` after policy initialization with their absolute module paths and versioned managed declarations. Tool names alone never grant trust. Builtin declarations cannot be replaced. Extensions have host privileges and must be trusted before loading them. No check here sandboxes arbitrary extension internals or prevents a trusted extension from changing inputs after our handler.

The shared active-policy registry is keyed by session ID, preventing coexisting SDK sessions from sharing modes or approvals. Switching sessions removes the previous entry; shutdown removes the current entry. A fingerprint includes mode, directives, tools and declarations so changing permissions also changes workflow replay identity.

Every subagent receives the mandatory auto-mode entrypoint and a versioned `PI_AGENT_POLICY` envelope. Child sessions cannot disable inherited policy, expand the parent tool list, or leave the canonical workspace. Approvals and classifier results are not inherited. Missing or malformed inherited policy data is rejected by the launcher or guard. Explicit local child extensions require a separate approval before process creation. A child inherits conservative limits even when the parent has switched auto mode off.

Workflow host capabilities also call the policy before reading files; source approval does not bypass those checks.

The worktree router defines the active workspace used by the parent policy and child launch checks. Absolute file paths remain absolute. Pi's original session cwd remains unchanged. Checks happen before execution; filesystem changes between validation and execution remain a limitation of host-process tools, not an OS isolation guarantee.

After inherited tool/cwd restrictions and protected filesystem boundaries, a classifier `safe` result permits an eligible explicitly allowed tool action, including shell calls and known custom tools. `ask` requires approval; `unsafe`, invalid output and classifier errors block. Shell composition remains part of the classifier request and prompt; this is model-based permission judgment, not an OS sandbox. Unknown extension tools still require trusted local declarations, an explicit local tool allowlist, or user approval; remote annotations do not grant permission.
